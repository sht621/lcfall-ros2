| 項目 | 承認済み仕様 |
|---|---|

| 送信ノード | `frame_publisher_node` |
| Pi→GPUサーバの出力トピック | `/synchronized_frame`（`/edge`接頭辞は付けない） |
| 確定済み内部トピック | `/sync/image`、`/sync/points`、`/sync/pair_info`、`/pose_frame`、`/points_roi` |

| 正常な人物未検出 | `PoseFrame.persons=[]` |

| ROI内0点／前処理失敗（v2.3採用） | **ROI結果が0点は正常処理**。XYZ＋`tag`のフィールド定義・元LiDAR `header.stamp`・変換後`frame_id`を維持した**空の`PointCloud2`をPublish**し、`SynchronizedFrame`として集約可能とする。**前処理そのものが失敗した場合はPublishしない**。別データで補完せず、集約側はタイムアウト時に破棄する |
| 元RGBの画像サイズ | カメラ出力解像度を固定し、サーバ側で事前設定。`PoseFrame`には`image_width`・`image_height`を含めない |
| COCO17の関節表現 | **`float32[17] keypoint_x`、`float32[17] keypoint_y`、`float32[17] keypoint_score`の固定長3配列を採用**。`Keypoint2D`構造体案は採用しない |
| 人物BBox・検出信頼度 | **`float32[4] bbox_xyxy`（元RGB画素座標、`[xmin, ymin, xmax, ymax]`）と`float32 detection_score`を採用** |
| 関節欠損の表現 | **明示的な欠損は`keypoint_x/y/score`の3値すべてNaN**。有限値を新たなしきい値で欠損扱いしない。部分NaN・Infは不整合 |
| その他の確定メッセージ定義 | **`PoseFrame`＝`std_msgs/Header header`＋`PersonPose[] persons`、`SyncPairInfo`＝`rgb_stamp`＋`lidar_stamp`（各`builtin_interfaces/Time`）**。余分な識別子・共通Header・画像サイズは追加しない |
| 集約のバッファと送信順序 | **有界バッファ、完成順Publish、容量超過時は古い未完成データから1件ずつ破棄、待機期限を超えた未完成データも破棄**。**初期上限は各入力10件、タイムアウトは1秒**（ともに暫定・ROS 2パラメータで調整可）。ATSの`queue_size=10`とは別 |
| 通常運用の状態表示 | **処理の成功状況と、同期不成立等のエラーをコンソールで確認できれば十分**。初期実装では永続ログ保存・詳細なデバッグログ・ログ集約の仕組みは作らない |
| 姿勢推定の入力・推論方式 | **`/sync/image`をROS 2で購読し、PythonからHailoRTへ直接渡す方式を第一候補に採用**。カメラを推論ノードから直接開かない。HEF・デコード・実機性能は要検証 |
| D455のRGB取得ドライバ | **`realsense2_camera`**。既存のデータ収集環境では`/camera/camera/color/image_raw`を使用。新しいPi環境での実出力トピックは要確認 |
| Docker配備 | **専用の新規Dockerイメージ1つ・単一コンテナを第一候補として採用**。内部にROS 2 Jazzy、HailoRT/Python、`realsense2_camera`、`livox_ros_driver2`、自作ノードを配置。既存`fall-collection`の両ドライバの構築方法を参考にし、収集・録画・Web管理機能は移植しない。Hailoドライバはホスト。`network_mode: host`を第一候補とし、デバイスは必要な権限のみ付与。互換性は実機未検証 |
| LiDAR座標変換とROI（v1.4–v2.0採用） | **LiDARはロボットに固定、検知領域はロボット前方のみ**。ロボットに固定した**転倒検知専用`fall_detection_frame`**へ静的TFでLiDAR点群を変換し、**同フレームで前方固定ROI**を適用する。基準姿勢での原点はLiDAR直下の床面、+Xは前方、+Yは左、+Zは上。`base_link`そのものをROI座標として採用しない。ロボットが移動・回転してもROIは本体と共に動く。地図固定ROI用の`map`／`odom`動的TFは不要。**ROI初期値はX: 1–8m、Y: −2–2m、Z: 0–2m（暫定）**とし、境界6値はROS 2パラメータで変更可能。**設置初期値として高さ0.85m・前方下向き25°を採用（暫定・変更可能）**。**学習時の床基準と同じ原点・軸の定義を目指し、初期実装にはロボットの傾き補正・追加の座標補正を入れない（v1.8採用）**。TF初期回転（Roll=0°、Pitch=+25°、Yaw=0°）は採用済み。ROIの最終値、TFの実測校正、学習時の`world`との実測整合性は未決定／要検証 |
| QoS・GPUサーバ受信（v2.2、v2.4で現状制約を追加） | **ドライバ→ATS：実Publisher互換**。**同期後のPi内部5経路および`/synchronized_frame`トピック：Reliable／Keep Last／Depth 10／Volatileを初期設定として採用**。**EdgeRMの現状**はサービスのみなので、サーバは暫定的にブリッジ経由のサービスで`SynchronizedFrame`を受信し、直接のトピック購読は**EdgeRMのトピック対応後**へ移す。通常ROS 2ノード・既存の最終トピック・メッセージは変更しない。Pi・サーバは同一ROS 2 Domain方針を維持し、RGB Imageはサーバで購読しない。トピック通信の新規経路とサービス経由の性能は実機未測定。`SendSynchronizedFrame.srv`（受信受付の`accepted`）を採用し、応答タイムアウト初期値0.5秒・自動再送なしを確定済み |
| EdgeRM通信切替（v2.4採用） | **Pi内部のROS 2トピック通信は可能**。4処理ノードを通常のROS 2で実装し、`frame_publisher_node`は従来どおり`/synchronized_frame`をPublishする。**EdgeRMがサーバ向けサービスにのみ対応する間は一時的なTopic→Serviceブリッジを追加**。トピック対応後はブリッジを外してGPUサーバが直接Subscribe。独自型の制約なし。**非同期`call_async()`、同時要求最大2件、未送信待機最新1件の上書きを暫定初期値として採用**。サービス型`SendSynchronizedFrame.srv`、応答の`accepted`、タイムアウト初期値0.5秒・自動再送なしを確定済み。**Pi 5の4コアでの持続10Hzは全系の実機試験待ち** |
| Livox入出力形式（v2.0採用） | **既存`fall-collection`のLivox設定を初期値として採用**：`xfer_format=0`、`publish_freq=10.0`（10Hz）、`frame_id=livox_frame`。`lidar_preprocess_node`の出力は**XYZ（float32）＋`tag`（uint8）のみ**とし、入力に含まれる`intensity`・`line`・各点の`timestamp`は転送しない。実際のPublisherフィールド・フレーム名はPi実機で確認 |

**未承認の項目を承認済みと推定しないこと。** LiDAR→専用`fall_detection_frame`への静的TFと同フレームでの前方固定ROIは承認済みだが、**TFの設置初期値（高さ0.85m、前方下向き25°）は採用済み（暫定）**。TFの初期回転はRoll=0°・Pitch=+25°・Yaw=0°と確認済みだが、校正済みの最終TF値、ROIの最終値、および学習時の床基準との実測整合は未決定／要検証（ROIのパラメータ化と暫定初期値は承認済み）。**初期実装では傾き・追加の座標補正を考慮しないことは承認済み**。**Livoxの既存設定（`xfer_format=0`、10Hz、`livox_frame`）とROI後のXYZ＋`tag`のみの出力は承認済み**だが、Pi実機での`tag`フィールド・型とドライバ出力の適合確認は必要。新しいPi環境でのRealSense・Livoxドライバの実出力トピック名、サーバ受信ノード名、採用したQoS初期設定の新規経路における実測適合性、状態表示の具体的な頻度・形式は未決定。**Pi・サーバ同一Domain、将来はサーバが`/synchronized_frame`のみ直接購読する方針は採用済み（現状はEdgeRMサービス経由）**。**集約バッファの各入力10件・タイムアウト1秒は暫定初期値として採用済み**であり、実機で調整する。単一コンテナは採用方針であり、技術的成立は実機検証が必要。

## 1. 目的・スコープ

### 1.1 目標

- エッジでカメラ画像から**複数人のCOCO17姿勢情報**を抽出し、LiDAR点群を所定の座標系へ変換して固定ROIを適用する。
- RGB–LiDARの**同期はエッジ側で確定**する。GPUサーバには、同じ同期ペアに由来する**骨格＋ROI点群を単一の複合メッセージ**で送る。
- RGB画像そのものは**GPUサーバへ送信しない**。EdgeRMの現行サービス通信では、Piのブリッジが`/synchronized_frame`から受け取った複合データのみをサービス送信する。将来のトピック対応後はGPUサーバが`/synchronized_frame`のみ購読する。同一Domainで画像トピックが発見可能でもよく、DDSレベルの厳密な隔離は要求しない。
- 姿勢推定ノードとLiDAR前処理ノードは独立させ、モデルや前処理を交換しやすくする。
- 初期段階は**計測・同期・姿勢推定・点群前処理・送信の成立**が目的。人物追跡・人物対応付け・転倒判定は実装対象外。

## 2. 採用済みアーキテクチャ

### 2.1 全体のデータフロー

```text
Raspberry Pi 5 / ROS 2 Jazzy

realsense2_camera (D455 RGB, ~30Hz) ───────┐
                                           │
                                           ▼
                                      sync_node
                                      ATS: RGB + LiDAR
                                           ▲
livox_ros_driver2 (PointCloud2, ~10Hz) ────┘
                                           │
                       ATSがペアを確定（~10Hzを期待）
                            ┌──────────────┼──────────────┐
                            │              │              │
                     selected Image   selected Cloud    SyncPairInfo
                            │              │              │
                            ▼              ▼              │
                 pose_estimation_node  lidar_preprocess_node
                   YOLOv8m-Pose        ロボット基準変換 + 前方固定ROI
                   複数人PoseFrame       PointCloud2
                            │              │              │
                            └──────────────┼──────────────┘
                                           ▼
                                    frame_publisher_node
                              元のstamp + 対応表で厳密照合
                              （ここでATSを再実行しない）
                                           │
                                           ▼
                                      SynchronizedFrame
                                骨格 + ROI点群の複合メッセージ
                                           │
                                           ▼
                                  GPUサーバ（受信・後続処理）
```

**LiDAR処理の位置づけ**：ロボット本体に剛固定したMid-360について、LiDAR→専用`fall_detection_frame`への静的TFとロボット前方固定ROIを採用する。停止時／移動時ともROIの定義をロボット基準で維持する。**地図・建物内の固定範囲を切り出す目的ではない**。

**命名の位置づけ**：4つの自作処理ノード（`sync_node`、`pose_estimation_node`、`lidar_preprocess_node`、`frame_publisher_node`）、内部5トピック（§5）、`/synchronized_frame`、`SynchronizedFrame`、2パッケージ名（§5）は**承認済み**。RGBドライバはRealSense D455用の`realsense2_camera`。新しいPi実機でのドライバ出力トピック名とサーバ受信ノード名は未決定。

### 2.2 設計原則（採用済み）

1. **先同期**：元RGB `Image`と元LiDAR `PointCloud2`をPi側のATSで対応付けてから処理する。LiDAR約10Hzに対し、全RGB 30fpsをYOLO推論しない。
2. **ATSは1回だけ**：最初に確定した同期ペアを後段で変更しない。集約ノードで再ATSはしない。
3. **並列前処理**：選択済みRGBと選択済み点群を、それぞれの独立ノードへ渡す。
4. **集約方式A（採用済み）**：`SyncPairInfo`で元RGB stampと元LiDAR stampの対応を通知し、処理結果の元stampの**完全一致**で集約する。各処理ノードはペアIDや他モダリティを知らない。
5. **標準メッセージの活用**：Pi内部の画像は`sensor_msgs/Image`、点群は`sensor_msgs/PointCloud2`を維持する。骨格と最終複合メッセージ、対応情報は必要最小限の定義を行う。
6. **タイムスタンプの保存**：RGB系結果には元画像の、LiDAR系結果には元点群の`header.stamp`を保持する。**同一値への書き換えや推論完了時刻による上書きはしない。**
7. **サーバ送信は1件の複合データ**：同期済みの骨格とROI点群を`SynchronizedFrame`として送信する。元RGB画像は含めない。EdgeRMがサービスのみ対応の間はTopic→Serviceブリッジ経由、トピック対応後はサーバの直接購読へ切り替える。

## 4. 集約方式A：対応表＋元の `header.stamp`

### 4.1 データの流れ

ATSが例えば次の2件をペアとして選択する（数値は説明用）：

```text
RGB   header.stamp = 12.005 s
LiDAR header.stamp = 12.000 s
差                    5.0 ms
```

`sync_node`は次の**3つを独立してPublish**する。

1. 選択済みRGB `sensor_msgs/Image` → `pose_estimation_node`
2. 選択済みLiDAR `sensor_msgs/PointCloud2` → `lidar_preprocess_node`
3. `SyncPairInfo(rgb_stamp=12.005s, lidar_stamp=12.000s)` → `frame_publisher_node`

各前処理ノードは入力の`header.stamp`を引き継いで出力する。LiDARの`frame_id`は静的TFによる変換後の**`fall_detection_frame`**へ更新する。

`frame_publisher_node`は`SyncPairInfo`と2つの処理結果を受信し、**元stamp同士の一致**で対応付ける。両結果が揃った時点で最終複合メッセージをPublishする。

### 4.2 メッセージ定義（承認済み。`fall_detection_msgs`）

**`SyncPairInfo.msg`（フィールド確定。具体仕様は§10）**

```text
builtin_interfaces/Time rgb_stamp
builtin_interfaces/Time lidar_stamp
```

- **`pair_id`は含めないと確定**。将来要件が変わった場合は改訂のうえ再検討する。
- 照合時は`sec`と`nanosec`、またはこれらから得られる**整数ns値**を使用する。浮動小数点秒へ変換して比較しない。

**RGB経路の姿勢結果（`PoseFrame.msg`、フィールド確定。詳細は§10）**

```text
std_msgs/Header header
PersonPose[] persons
```

- **少なくとも複数人を表現**し、初期段階で追跡IDを仮定しない。
- **正常な人物未検出は`persons=[]`（承認済み）**。ノード処理失敗とは区別する。
- **関節配列形は固定長3配列として採用済み**。人物BBox・検出スコアと、欠損関節のNaN三値セットの規約も**採用済み**。実際のHailo出力との接続は実装時に検証する。

**LiDAR経路の結果**

```text
sensor_msgs/PointCloud2
# header.stamp: 元LiDAR計測時刻
# header.frame_id: 座標変換後のフレーム
# points: 固定ROI後の可変点数の点群
```

**最終同期フレーム（`SynchronizedFrame.msg`、型名・フィールド確定。詳細は§10）**

```text
PoseFrame pose
sensor_msgs/PointCloud2 points
```

- `pose.header.stamp`と`points.header.stamp`の双方を保持する。
- `SyncPairInfo`の二つのstampは、複合メッセージ内の二つのheaderから再取得できるため、**二重格納しないと確定**。
- **`PoseFrame`・`SyncPairInfo`・`SynchronizedFrame`のフィールド定義と`fall_detection_msgs`パッケージ名は確定**。

### 4.3 集約処理の最小アルゴリズム

```text
対応表: (rgb_stamp_ns, lidar_stamp_ns) の集合
姿勢待ち: rgb_stamp_ns → PoseFrame
点群待ち: lidar_stamp_ns → PointCloud2

PairInfo受信  → 対応表へ登録 → assembleを試行
Pose受信      → 姿勢待ちへ登録 → assembleを試行
Cloud受信     → 点群待ちへ登録 → assembleを試行

assemble:
  対応表にある (rgb_ns, lidar_ns) の両結果が存在したら
  → SynchronizedFrame(pose, cloud) を1件Publish
  → 対応表と使用済み結果を削除
```

- **トピック間の受信順序は保証しない**。`PairInfo`より姿勢／点群が先に来ても集約できる設計とする。
- 先行するATSペア情報をキーに照合し、**再度スロップ付き近傍探索はしない**。
- **集約待機バッファは有界（採用済み）**。満杯で新しいデータを受け付ける際は、古い未完成データを1件ずつ破棄し、保持数を上限内に戻す。期限を超えて未完成のデータも破棄する。`PairInfo`より先に届いた姿勢・点群も保持上限／期限の管理対象。**暫定初期値はPairInfo・PoseFrame・PointCloud2の各待機入力10件、タイムアウト1秒（ROS 2パラメータで変更可能）**。受信からの待機時間は単調時計で管理し、センサ`header.stamp`は経過時間計算に流用しない。ATSの`queue_size=10`とは別管理。
- 同一stampの異なるデータが実際に観測された場合は診断対象とする。通常発生を前提に独自IDを導入しない。
- **両結果が揃ったペアから完成順にPublishする（採用済み）**。計測時刻順とは一致しない場合があるため、GPUサーバ側の時系列処理に必要な並べ替え・欠落処理は別途検討する。

### 4.4 標準メッセージを維持する設計意図

- `pose_estimation_node`: **`Image → PoseFrame`のみ**。ATSやLiDAR、ペアIDを知らない。
- `lidar_preprocess_node`: **`PointCloud2 → PointCloud2`のみ**。RGBやペアIDを知らない。
- 対応関係は`sync_node`と`frame_publisher_node`だけが扱う。
- 全処理ノードは自作予定なのでID付きラッパーも実装可能。ただし今回のAは**同期の責務を処理ノードから切り離すこと**を重視した選択であり、Bを技術的に不可能とみなしていない。

### 5.1 EdgeRMによるサーバ通信の暫定切替（v2.4で方針採用）

- **前提**：EdgeRMは現時点でサーバへの**ROS 2サービス通信のみ**対応するが、将来トピック対応予定。独自メッセージ型への制約はなく、**Pi内部の通常のROS 2トピック通信も利用できる**。EdgeRM化は通常のROS 2ノードへ少量の変更を追加する方式と確認済みであり、4処理ノードに特別なEdgeRM前提を持ち込まない。
- **現在**：`frame_publisher_node`は既定の`/synchronized_frame`をPublishするだけ。**一時的な`topic_to_service_bridge_node`**がこれをSubscribeし、`SynchronizedFrame`を含むROS 2サービス要求としてサーバへ転送する。
- **将来**：EdgeRMでトピック送受信できるようになったら、**ブリッジをLaunch構成から外す**。GPUサーバは`/synchronized_frame`を直接Subscribeする。**4処理ノード、内部5トピック、`SynchronizedFrame.msg`は変更しない**。
- **実装の境界**：ブリッジは`fall_detection_edge`パッケージ内に一時ノードとして追加する案。サービス型は**`fall_detection_msgs/srv/SendSynchronizedFrame.srv`**と確定。既存の`SynchronizedFrame`をリクエストで渡し、サーバが**受信を受け付けたか**を`bool accepted`で早期に返す。転倒判定結果の返信はこの通信の責務に含めない。サービスのROS 2エンドポイント名は実装時に設定する。
- **送信制御（v2.5で暫定初期値を採用）**：`/synchronized_frame`を受信して、ROS 2の`call_async()`で**非同期サービス要求**を送る。**同時に応答待ちできる要求は最大2件**、それ以上は**未送信待機の最新1件のみ**を保持する。待機枠が埋まった状態でさらに新しいフレームが来た場合、**古い未送信フレームを上書きして破棄**する。要求の応答・タイムアウトで送信枠が空けば、待機中の最新フレームを送る。**前処理ノードと集約ノードをサービス応答待ちで止めない**。
- **タイムアウト・失敗（v2.6で仕様確定、実機動作は未検証）**：応答タイムアウトの**暫定初期値は0.5秒（500ms）**とし、ROS 2パラメータ`request_timeout_sec`で変更可能にする。`accepted=true`を受付成功、`accepted=false`または通信例外・期限超過を受付失敗／結果不明として扱う。期限切れ要求のクライアント側の待機管理を解放し、成功と誤表示しない。**失敗・タイムアウト時に自動再送しない**。ただしタイムアウトはサーバ側の受信取消を意味せず、受信済み／未受信が不明な場合もある。コンソールには簡潔な警告を表示する。EdgeRMが同時2件の非同期要求を扱えるか、約10件/秒を受け付けられるかは**実機未検証**。既存の集約待機バッファ（各入力10件・1秒）とは**別の送信待機管理**である。
**確定したサービス型（`fall_detection_msgs/srv/SendSynchronizedFrame.srv`）**：

```srv
SynchronizedFrame frame
---
bool accepted
```

`accepted`は**サーバの受付成否**であり、転倒検知の推論成否ではない。ブリッジの暫定初期値は次のとおり。いずれもROS 2パラメータで変更できるようにする。

```yaml
topic_to_service_bridge_node:
  ros__parameters:
    max_in_flight_requests: 2
    pending_buffer_size: 1
    request_timeout_sec: 0.5
```

- **QoSについて**：確定済みの`/synchronized_frame`のトピックQoSはそのまま。サーバへの**現行サービス区間**はこのトピックQoSと同一の配送保証が適用されるわけではないため、別途性能・応答時間・欠落を確認する。

### 5.3 姿勢推定ノードとHailoRTの接続（v1.1採用方針）

- `pose_estimation_node`は**`/sync/image`（`sensor_msgs/Image`）を購読**し、同期後に選択された画像だけを処理する。推論ノード自身はカメラデバイスを開かない。
- **第一候補はPythonからHailoRTを直接呼ぶ方法**。ROS 2 Imageから画像配列へ変換 → HEFの入力形式に前処理 → HailoRT実行 → YOLOv8m-PoseのBBox／COCO17関節／信頼度をデコード → 元RGB画像の画素座標へ復元 → 承認済み`PoseFrame`をPublishする。入力`Image.header`を保持し、正常な0人検出と推論失敗を混同しない。
- **GStreamerを姿勢推定経路に挟む方法は初期候補としては選ばない**。既存のHailo資産がGStreamer専用で、直接呼出しに使えるHEF・後処理が整っていない場合は、実測と開発負荷に基づいて再検討する。
- **未検証**：手元のYOLOv8m-Pose HEFがHailoRT直接推論・必要な後処理に対応するか、入力スケーリング／レターボックス座標の逆変換、複数人の検出値と欠損値の表現、約10Hz連続動作・画像キュー蓄積の有無。
- **Docker構成は単一コンテナを第一候補として採用済み（v1.2）**。ROS 2 Jazzy、HailoRT／Python、`realsense2_camera`、`livox_ros_driver2`、自作ノードを同居させる。ホストPCIeドライバ、コンテナ内Pythonバインディング（ARM64・Python ABI）、Hailo/RealSenseデバイスアクセス、LiDAR通信の実機互換性は未検証。

- **専用の新規Dockerイメージ1つ・単一コンテナ（採用方針）**：`ros:jazzy-ros-base`のARM64対応イメージをベース候補とし、Ubuntu 24.04 / ROS 2 Jazzy、HailoRT／Pythonバインディング、`realsense2_camera`（D455 RGB）、`livox_ros_driver2`（Mid-360）、`fall_detection_msgs`、`fall_detection_edge`を配置する。
- **既存資産の扱い（採用方針）**：`fall-collection`のRealSense RSUSBバックエンド・`realsense2_camera`のビルド設定、Livox SDK2・`livox_ros_driver2`のビルド設定、USBアクセス・通信設定を**参考・再利用候補**とする。ただし既存の複数コンテナや録画・収集・Web管理機能をそのまま持ち込まない。既存Dockerイメージをそのまま転用するという決定ではない。
- **Compose・デバイス設定（第一候補）**：`network_mode: host`でMid-360の通信とROS 2接続を単純化し、Hailoは実機で存在を確認した`/dev/hailo0`、RealSenseは必要なUSBデバイスとアクセス権をコンテナへ渡す。**`privileged: true`は原則使わず**、必要なデバイス・グループ権限のみ付与する。必要なデバイスパス・グループ・Livox IP設定はPi実機で確定する。
- **起動方法（採用方針）**：ドライバと自作4ノードをROS 2 Launchから管理する。具体的なLaunch構成と起動順・再起動時の挙動は実装時に検討する。
- **実機確認**：HailoRTとホストドライバのバージョン整合、ARM64・Python ABI、`/dev/hailo0`へのアクセス、RealSense D455のUSB認識・RGB取得、Mid-360の点群取得、各ドライバ／自作ノードの同時動作、約10Hz追従を確認する。**上記のCompose値は採用する構築方針であり、実機で正常動作が立証済みという意味ではない。**
- **代替案**：必要な互換性が成立しなかった場合のみ、Hailo推論環境などのコンテナ分離を再検討する。初期設計から複数コンテナにはしない。

**参考（実機適合を保証しない）**：Hailo公式Python standalone pose estimationサンプル https://github.com/hailo-ai/hailo-apps/blob/main/hailo_apps/python/standalone_apps/pose_estimation/README.md 、Hailo公式のコンテナ前提条件 https://github.com/hailo-ai/hailo-apps/blob/main/doc/user_guide/prerequisites.md 。

**ネットワーク境界（v2.2採用、v2.4で暫定サービス経路を追加）**：PiとGPUサーバは**同一`ROS_DOMAIN_ID`で通信**する。GPUサーバは**現在はEdgeRMサービスで`SynchronizedFrame`を受信し、将来は`/synchronized_frame`のみ購読する。いずれもRGB画像トピックのSubscriberを作らない**。同じDomainに属する画像トピックはサーバから発見・購読可能な場合があるが、**DDSレベルでの厳密な隔離は要求しない**。したがって、画像隔離のためのDomain分離・Gateway・独自中継は初期実装に導入しない。画像本体が意図せず流れていないことは実機で確認する。

### 5.5 LiDAR前処理の座標系とROI（v1.4–v2.0採用方針）

- **取り付けと検知範囲（採用済み）**：Mid-360はロボット本体に剛固定され、検知するのは**ロボット前方のみ**。
- **専用フレーム（v1.5採用済み）**：ROIを`base_link`に直接定義せず、ロボット本体に固定した**`fall_detection_frame`**を設ける。基準姿勢での原点はLiDAR計測原点の鉛直床投影（LiDAR直下の床面）、**+Xはロボット前方、+Yは左、+Zは上**。基準姿勢・床面・取り付け高さは実機で確認する。このフレームは建物に固定した`world`ではなく、ロボットと一緒に動く。
- **座標変換（採用済み）**：LiDARフレームから`fall_detection_frame`へ**静的TF**で変換する（必要なら既存の`base_link`との静的TF連鎖を使用）。`PointCloud2.header.stamp`は元LiDAR時刻を維持し、変換後の`header.frame_id`を**`fall_detection_frame`**とする。
- **取り付け値と静的TFの初期設定（v1.7・v1.9採用済み、暫定）**：LiDAR計測原点の床からの高さは**0.85m（85cm）**、前方下向き**25°**。**LiDAR本体の+X軸をロボット前方へ向けて設置する**と確認済み。この取り付け前提で、親フレーム=`fall_detection_frame`・子フレーム=LiDAR点群の実際の`header.frame_id`とし、TF初期値を並進 **(x,y,z)=(0,0,0.85)m**、RPY **(roll,pitch,yaw)=(0,+25°,0)**、すなわちpitch約**+0.436332rad**とする。ROS右手系で+Y軸回りの正回転は+Xを下方へ向ける。**これらは実測済みの最終外部校正値ではない**。値は設定ファイルで変更可能とし、実際の点群フレーム名と既存TFを照合して重複発行しない。
- **ジャーナルとの根拠の区別（v1.9確認）**：ジャーナル研究計画v3.11の§4.5は**変換後の`world`座標について+X=人物方向、+Y=左、+Z=上**と定義し、§3.1では固定設置のMid-360の**高さ0.80m・下向き25°**を計画値としている。**LiDAR本体+Xの物理的な取り付け向きがジャーナル本文に明記されているわけではない**。ロボットの「本体+Xが前方」という追加確認に基づき初期RPYを定めた。ジャーナルの0.80mとロボットの0.85mは異なる設置条件であり、取り違えない。
- **ROI（採用済み）**：`fall_detection_frame`で**前方固定ROI**を適用する。ロボットが移動・回転してもROIは本体と一緒に移動する。**地図固定座標`map`／`odom`への動的TF変換は本処理に追加しない**。
- **初期ROI値（v1.6採用済み、暫定）**：ジャーナルの初期検証候補をエッジ側でも**初期設定**として使用する：**X=1.0–8.0m、Y=−2.0–2.0m、Z=0.0–2.0m**。実機での検知範囲・床基準との整合を確認して調整するため、最終的なROI値としては確定しない。
- **設定方法（v1.6採用済み）**：6つの境界値（`roi.x_min`、`roi.x_max`、`roi.y_min`、`roi.y_max`、`roi.z_min`、`roi.z_max`）を`lidar_preprocess_node`のROS 2パラメータとして指定し、ソースコード変更なしで調整可能にする。例：

  ```yaml
  lidar_preprocess_node:
    ros__parameters:
      roi:
        x_min: 1.0
        x_max: 8.0
        y_min: -2.0
        y_max: 2.0
        z_min: 0.0
        z_max: 2.0
  ```
- **学習時の座標系との対応（v1.8採用済み）**：固定設置のジャーナル`world`と本エッジの`fall_detection_frame`で、**原点の定義（LiDAR直下の床面）、軸方向（前方X・左Y・上Z）、単位（m）**を一致させる方針を維持する。ただし前者は設置場所に固定、後者はロボットに固定されるため、**数値上の一致や学習済みモデルでの精度を保証するものではない**。**初期実装にロボット傾斜に対する姿勢補正やその他の追加座標補正を入れない**。水平な床面を前提に、床の点がおおむね`Z=0`、前方が`X>0`、左方が`Y>0`、ROI後も対象人物の点が残ることを実機で確認する。
- **Livoxドライバ初期設定（v2.0採用済み）**：既存`fall-collection`の`livox.example.yaml`を参照し、`xfer_format=0`（標準`PointCloud2`形式）、`publish_freq=10.0`（10Hz）、`frame_id=livox_frame`を初期設定として流用する。Piでの実出力`header.frame_id`・フィールド構成と`tag`の型は実機確認する。設定ファイルのデバイスIPなどはPi用に別途設定する。
- **ROI後のデータ契約（v2.0採用済み）**：点数は可変長とし、`lidar_preprocess_node`は入力のXYZをTF変換・ROI抽出し、同じ点の`tag`（`uint8`）を保持して、**XYZ（`float32`）と`tag`（`uint8`）の4フィールドだけの`PointCloud2`**をPublishする。元入力に含まれていても`intensity`・`line`・各点の`timestamp`は後段へ転送しない。`tag`が存在しない、または型が不適合なら架空の`tag`を生成せず、入力契約の不一致として扱う。**ROI後が0点でも正常結果として空の`PointCloud2`をPublishする**。前処理自体が失敗した場合は結果をPublishせず、`frame_publisher_node`が既定の未完成ペアの待機・破棄を行う（v2.3採用）。256点化・床除去・SOR・RANSACは初期前処理に追加しない。
- **未決定／要確認**：静的TFの最終的な実測校正値（初期値は並進(0,0,0.85)m・RPY(0,+25°,0)）、**前方ROI初期値の実測適合性と最終的なXYZ範囲**、ジャーナル固定床基準`world`との厳密な整合性。**ロボットの傾斜に対する補正は検討対象外**。移動中の点群歪みやモデル検知精度への影響は後続の評価課題とし、初期実装にdeskew等の追加処理は採用しない。

## 6. エラー・欠測・QoS・実機試験

### 6.1 成立すべき入力・出力契約

| 条件 | 現段階の扱い |
|---|---|
| ATS同期不成立 | 疑似ペアを作らず、簡潔な同期状態・不成立をコンソールで確認できるようにする。ATS成功コールバックだけでは不成立を直接通知しないため、元入力と成立件数の観測方法は実装時に検討する |
| 人物が0人 | **採用済み**：正常な推論完了結果として`persons=[]`のPoseFrameを出力。推論処理失敗と区別する |
| ROI後の点数が0 | **採用済み（v2.3）**：正常なROI処理結果として、点数0の`PointCloud2`をPublishする。XYZ＋`tag`のフィールド定義・元LiDARの`header.stamp`・変換後の`frame_id`を維持する。集約側は受信成功として扱い、骨格・PairInfoが揃えば通常どおり送信する。N点への偽装・補間はしない |
| Poseまたは点群前処理が失敗 | **採用済み**：正常な人物0人／ROI 0点とは区別する。失敗した処理結果をPublishせず、別ペアのデータで補完もしない。集約側では未完成のまま待機し、期限到達時に破棄する。処理失敗の具体的なコンソール表示形式は実装時に調整 |
| PairInfoが届かない | A方式に固有の追加依存。後から来る可能性を踏まえたバッファを設計する |
| ROS 2再起動・古い結果 | どの方式にも必要な一般的なライフサイクル管理。集約状態の初期化・残留管理を実装する |

**正常な人物未検出・ROI後0点と、ノード自体の処理失敗・通信欠落を区別する**。初期段階はコンソールで最小限の状態・異常が確認できることを優先し、詳細な診断機構は必要になってから追加する。

### 6.2 QoS（v2.2：初期方針採用済み・新規経路は実測待ち）

- **RealSense・Livox → `sync_node`**：各ドライバの実Publisherが提示するQoSと互換のあるSubscriberを構成する。既存`fall-collection`のPublisher QoS確認方法を参考にし、Best EffortのPublisherへReliable購読を要求する等の非互換を避ける。
- **ATS後のPi内部5経路**（`/sync/image`、`/sync/points`、`/sync/pair_info`、`/pose_frame`、`/points_roi`）：**Reliable／Keep Last／Depth 10／Volatile**を初期設定とする。
- **`/synchronized_frame`トピック**：**Reliable／Keep Last／Depth 10／Volatile**を初期設定とする。EdgeRMトピック対応後、GPUサーバのSubscriberにもこのQoSを適用する。**現時点のGPUサーバ向け送信はサービス経由**であり、トピックQoSと区別する。サーバでATSを再実行しない。
- **実測で確認**：各Publisher/SubscriberのQoS互換性、連続10Hzでの配送、欠落・遅延・処理滞留、通信量。既存MCAP再生環境の検証済み設定と、新規Pi通信経路の動作検証は区別する。
- **Reliableでもアプリ側の処理遅延やバッファ超過は解消されない。** 集約バッファの制限と破棄方針は引き続き適用する。

### 6.3 通常運用の表示方針（採用済み）

- **コンソールで、処理が継続して成功しているか、同期不成立・処理失敗等が発生していないかを簡潔に確認できればよい**。大量のフレーム別詳細ログや永続的な診断履歴は初期要件に含めない。
- **初期実装ではログを自前でファイル保存しない**。デバッグ用の詳細ログ、定期集計・ログローテーション等の専用仕組みも今は作らない。必要になった時点で追加を検討する。
- ROS 2／Dockerの標準出力や既定のファイル記録の有無は起動環境に依存するため、**「コンソールで確認する」という運用方針に合わせて既定設定を確認する**。専用の永続ログ保存機能を追加する決定ではない。
- **未決定**：成功表示の周期や具体的な書式。詳細な欠落分析や長期集計は必要性が生じた際に検討する。

### 6.4 実機での最小確認項目

1. カメラとLivoxの**`header.stamp`の時計・エポック・計測時刻基準**が比較可能かを確認。
2. ジャーナル初期設定のATSで、入力件数・同期成功率・RGB–LiDAR時刻差・連続同期失敗を測定。
3. ATSで採用したRGBだけをYOLOv8m-Poseへ渡し、**持続約10Hz**で追従できるか確認（Hailo単体FPSとは区別）。
4. Pi上でLiDARドライバ・**LiDAR→ロボット基準の静的TFと前方固定ROI**・Pose・集約を同時動作させ、取り付け座標と床高さを確認し、CPU・メモリ・温度・入力/出力Hz・キューを計測。
5. 三つのトピックの**到着順が入れ替わる**テスト、片側の欠落・未検出・0点・遅延・再起動時のテスト。
6. 出力された各`SynchronizedFrame`がATSの選択した**元stampペアと一致**することを検証。
7. 現行EdgeRMサービス経由で複合メッセージの通信量・遅延・欠落・応答時間・滞留を計測。将来のトピック対応後は同じ`SynchronizedFrame`のトピック経路を検証。RGB画像が意図せず転送されないことを確認。
8. Raspberry Pi 5の4コアで、**RealSense RGB／Livox 10Hz／Hailo推論前後処理／TF・ROI／集約／サービス通信を同時起動**し、持続10Hzの処理・CPU占有率・温度・バッファ滞留を測る。推論単体FPSから成立を断定しない。

### 8.2.1 待機バッファの満杯時ポリシー

| 案 | 状態 | 理由 |
|---|---|---|
| **古い未完成データから1件ずつ押し出す** | **採用済み** | 新しいペアを継続して受け付け、過去の遅延がオンライン処理に波及するのを防ぐ |
| 新しいデータを破棄して既存ペアを保護 | **不採用（現段階）** | リアルタイム性に重要な新しいデータを優先したいため |
| 容量が空くまで入力を待機させる | **不採用（現段階）** | 上流の同期・推論へ遅延を伝播させる可能性があるため |

待機期限を超えた未完成データも破棄する。**初期値は各入力（PairInfo・PoseFrame・PointCloud2）10件、待機タイムアウト1秒**。いずれも暫定値としてROS 2パラメータで変更可能にし、実測後に調整する。通常運用で必要な最小限の状態・エラーはコンソールで確認し、詳細ログ・永続保存は初期実装に含めない。

### 8.3 機能と前処理（**却下と保留を区別**）

| 項目 | 状態 | 理由・位置づけ |
|---|---|---|
| RGB画像のサーバ送信 | **不採用** | 画像をPi側で骨格化して通信量を抑える。同一Domainで画像トピックが見えることは許容し、サーバで画像を購読しない方針で十分と判断 |
| 画像隔離のためのDomain分離／Gateway導入 | **現段階では不採用（v2.2）** | サーバが現在は複合データのみをサービス受信し、将来は`/synchronized_frame`のみ購読すれば十分という要件のため、DDSレベルでの厳密な隔離は不要。実機で想定外の配送がないか確認する |
| 初期段階での人物追跡・転倒判定 | **現段階では対象外** | まず複数人骨格・点群・通信の成立を確認。後続段階の検討対象 |
| 床除去・SOR・RANSAC・点群人物抽出 | **未決定／未採用** | ジャーナル同様に観測品質を確認する前に導入しない。必要なら効果と人体点の欠落を比較 |
| ROI出力の一律256点化 | **不採用** | N=256は後段モデル入力に関する暫定条件。中間のROI点群は可変点数を保つ |
| ROI 0点を前処理失敗とみなして出力を抑止 | **不採用（v2.3）** | 正常にROI抽出できた結果0点と、TF・フィールド不整合等による処理失敗を区別する。空点群は正常な観測結果として出力する |
| 地図固定（`map`／`odom`）ROIのための動的TF | **現段階では不採用** | 対象はロボット前方のみで、LiDARは本体に固定。ロボット固定`fall_detection_frame`への静的TFと前方固定ROIで目的を満たすため。将来、特定の建物内位置を切り出す要件が出れば再検討 |
| ROI座標系に`base_link`をそのまま使う案 | **不採用（v1.5で専用フレームに変更）** | 既存`base_link`の原点が床面上とは限らず、学習時の床高さとの整合を取りにくい。ロボットの既存フレームを変えずに転倒検知用の原点・軸を定義するため |
| YOLOv8s-Poseへの変更 | **代替候補・未決定** | mモデルの10Hz追従が不可能だった場合に速度と精度を比較する。現時点で自動切替しない |
| 単一Dockerコンテナ | **第一候補として採用済み（実機未検証）** | 新規専用イメージ1つにROS 2 Jazzy＋HailoRT＋`realsense2_camera`＋Livox＋自作ノードを同居させ、既存収集システムのドライバ設定を参考にする。ARM64・Python ABI、ホスト側Hailo PCIeドライバ／デバイスアクセス、RealSense USBアクセス、LiDAR通信を実機で確認する |
| Pose処理にGStreamerを介在させる案 | **代替候補（第一候補としては不採用）** | ROS 2の同期済みImageを直接PythonからHEFへ投入する方が経路を短くできる。手元の資産がGStreamer前提なら再検討 |

### 8.4 EdgeRMへの段階的移行（v2.4採用）

| 案 | 状態 | 理由 |
|---|---|---|
| **既存4ノードは通常ROS 2のまま、現行はTopic→Serviceブリッジを一時追加** | **採用済み** | EdgeRMが現状サーバ間サービスのみ対応し、将来はトピックに対応予定。処理ノードや複合メッセージを変更せず通信経路だけ切り替えるため |
| 現行EdgeRMサービス通信を`frame_publisher_node`へ直接組み込む | **不採用** | 将来のトピック対応時に集約ノードの通信責務を改修することになるため |
| EdgeRMのためにPi内トピック通信や単一Dockerを全面再設計する | **不要** | Pi内トピック通信に問題なく、EdgeRM対応は通常ROS 2ノードに少量の変更を追加すればよいという確認による |
| ブリッジでサービス応答を逐次待つ／未送信フレームを無制限にためる | **不採用（v2.5）** | 10Hzの継続処理とエッジ側のリアルタイム性を損ねるため。非同期呼び出しと上限付きの最新1件待機を採用 |
| サービス失敗・タイムアウト時の古いフレームの自動再送 | **不採用（v2.6）** | オンライン処理に遅れや重複を持ち込まないため。必要なら後段の運用要件で再検討する |

### 10.1 設計条件と既存型の検討

- `sync_node → pose_estimation_node`：`sensor_msgs/msg/Image`を使用。ヘッダーは元画像のものを維持。
- `sync_node → lidar_preprocess_node`：`sensor_msgs/msg/PointCloud2`を使用。入力stampを維持。
- `lidar_preprocess_node → frame_publisher_node`：標準`PointCloud2`を使用。`frame_id`は座標変換後の適切なフレームに更新。**tagを維持**。
- `vision_msgs`の`Detection2D`はBBox等に対応するが、**COCO17の関節XY＋関節ごとのscore＋欠損契約を一つの検出に直接持たせる標準フィールドはない**。`vision_msgs`への無理な流用はせず、必要な骨格用型を明確に定義することを第一候補にする。Jazzyの既存メッセージ導入の可否を実装前に最終確認する。
- **独自メッセージは4ファイルでフィールド構成確定**：`SyncPairInfo.msg`、`PersonPose.msg`、`PoseFrame.msg`、`SynchronizedFrame.msg`。**`fall_detection_msgs`に配置することを承認済み**。
- 人物追跡ID、画像そのもの、モデルの内部特徴、N=256点群、GPUサーバ側ATS情報を追加しない。モデル設定・バージョンなどの再現性情報は原則として実行設定／ログで管理し、毎フレームの必須フィールドを増やさない。

### 10.2 `SyncPairInfo.msg`：ATSで確定した対応関係

```text
# fall_detection_msgs/msg/SyncPairInfo.msg（フィールド・パッケージ名確定）
builtin_interfaces/Time rgb_stamp
builtin_interfaces/Time lidar_stamp
```

- 各値は**入力`Image.header.stamp`／入力`PointCloud2.header.stamp`の複写**。受信時刻や処理完了時刻ではない。
- 両stampを同じ値に丸めない。**両方の時刻の組**が初回ATSで確定した対応関係。
- **同期ペア番号・共通Header・時差の計算結果は含めない**。時差は2つのstampから算出できる。将来必要になれば改訂で検討する。
- 集約時は`(sec, nanosec)`の組または整数nsで**完全一致**照合する。浮動小数点に変換して比較しない。

### 10.3 `PersonPose.msg`：1人物分のCOCO17姿勢（主要フィールド・欠損規約は採用済み）

```text
# fall_detection_msgs/msg/PersonPose.msg（フィールド・パッケージ名確定）
# 元RGB画像の画素座標系。bboxは[x_min, y_min, x_max, y_max]。
float32[4] bbox_xyxy
float32 detection_score

# COCO17の関節indexを共有し、すべて元RGB画素座標。
float32[17] keypoint_x
float32[17] keypoint_y
float32[17] keypoint_score
```

- **1メッセージ＝1人物**。複数人は`PoseFrame.persons[]`へ格納。初期段階では人物追跡IDなし。
- `bbox_xyxy`は元RGB解像度の座標で、YOLO入力用のリサイズ・letterbox後の座標ではない。出力後に元解像度へ戻す。`detection_score`も元の検出結果を保持する。
- 関節番号は通常の**COCO17順序**で固定：`0 nose, 1 left_eye, 2 right_eye, 3 left_ear, 4 right_ear, 5 left_shoulder, 6 right_shoulder, 7 left_elbow, 8 right_elbow, 9 left_wrist, 10 right_wrist, 11 left_hip, 12 right_hip, 13 left_knee, 14 right_knee, 15 left_ankle, 16 right_ankle`。
- **有効な推定結果のconfidenceが低いという理由だけで関節を欠損化しない。** ジャーナルv3.11の「新しい閾値で有限な値を捨てない」原則を継承。
- **明示的な関節欠損があるときのみ**`x/y/score`の3値とも`NaN`で表す（承認済み）。部分NaN・無限大は不整合として拒否。モデルが出す`0`を欠損と勝手に同一視しない。Hailoのデコード仕様を実機で確認する。
- 関節を`(0,0,0)`にするのは**後段分類器へ渡すモデル入力コピー**の変換段階であり、この中間メッセージでは行わない。
- BBox・検出スコアの値域や元モデルの人物選択条件は実装時に照合する。新たな信頼度しきい値を本書では決めない。

**承認済みの設計意図**：COCO17の関節数が固定で、ジャーナルのXY＋score配列へ移しやすく、追加の独自`Keypoint2D.msg`型を設ける必要がないため、関節は固定長3配列を採用。**3配列自体がROS 2の標準形式という意味ではない。** ジャーナルと合わせ、元RGB画素座標のBBox（`bbox_xyxy`）、人物検出信頼度（`detection_score`）を保持し、明示的な関節欠損はX/Y/scoreの3値NaNで表す。なお**Hailo実機出力のデコードと欠損値の対応は未検証**。

### 10.4 `PoseFrame.msg`：同期選択済みRGBの骨格結果（フィールド確定）

```text
# fall_detection_msgs/msg/PoseFrame.msg（フィールド・パッケージ名確定）
std_msgs/Header header
PersonPose[] persons
```

- `header.stamp`は選択された**元画像**のstamp。`header.frame_id`も元画像のフレーム識別を維持し、2D画素座標を`world`であるかのように扱わない。
- **`image_width`・`image_height`はメッセージに含めない（承認済み）**。カメラの元RGB出力解像度を固定し、GPUサーバ側に事前設定する。Poseノードの推論用リサイズ後解像度とは区別する。設定不整合は検証対象。
- **正常に推論が終了して人物が0人**：`persons=[]`の`PoseFrame`をPublishする（**承認済み**）。ノード異常による推論失敗は同じ空配列で偽装しない。
- 人物数が複数の場合は全件を配列で出す（モデルが返した検出結果の範囲内）。時間方向の人物追跡・IDの付与はしない。
- ジャーナルの`frame_idx`は同期済みTrialを保存するときの連番に相当し、**現段階のライブROSメッセージに架空のframe_idxを新設しない**。後段が必要なら、入力順と元stampから別途生成する。
- **`detection_status`等の追加フィールドは今回採用しない**。正常な0人（空配列）と処理失敗（結果未出力＋診断）を区別して運用する。

### 10.5 LiDAR結果の`PointCloud2`契約（標準型のまま）

```text
sensor_msgs/PointCloud2  # 独自ラッパーなし
header.stamp             # 元LiDARの計測時刻を維持
header.frame_id          # TF変換後のfall_detection_frame（確定）
fields                   # x,y,z: FLOAT32、tag: UINT8（出力4フィールドのみ、確定）
width / height / data    # ROI後の可変点数を表現
```

- **v2.0採用済み**：LiDAR入力は既存`fall-collection`の`xfer_format=0`・10Hz・`livox_frame`設定を初期値に使用する。**ROI後の出力フィールドはXYZ（`float32`）＋`tag`（`uint8`）のみ**。入力の`intensity`・`line`・各点の`timestamp`は転送しない。ジャーナル実装と同じくROIマスクに対応する元`tag`を保持し、**モデル入力TensorではXYZのみ使用する**。実機で入力`tag`の存在・型を確認し、欠けていた場合は値を捏造しない。
- 変換・ROI後は可変点数。`N=256`への調整、床除去、SOR、RANSAC、人物領域切出しはこのノードに無断追加しない。
- **採用済み**：LiDARが本体に固定され、ロボット前方のみを扱うため、LiDAR→ロボット固定の**`fall_detection_frame`への静的TF**と**同フレーム上の前方固定ROI**を使用する。基準姿勢では原点がLiDAR直下床面、+X前方・+Y左・+Z上。移動時も同じロボット相対ROIを用い、地図固定ROI向けの`map`／`odom`動的TFを初期処理に要求しない。**初期ROIはX=1–8m、Y=−2–2m、Z=0–2mをパラメータで設定（暫定）**。ジャーナルの固定床基準`world`とは異なり得るため高さ・軸・モデル入力の整合を検証し、最終ROI値を調整する。
- **ROI後0点は正常系（v2.3採用）**：XYZ＋`tag`のフィールド定義と元LiDAR `header.stamp`、`fall_detection_frame`の`frame_id`を持つ空`PointCloud2`をPublishする。前処理失敗時はPublishしない。集約側は0点と処理失敗を混同しない（§6.1参照）。

### 10.6 `SynchronizedFrame.msg`：GPUサーバ向け複合メッセージ（型名・フィールド確定）

```text
# fall_detection_msgs/msg/SynchronizedFrame.msg（フィールド・パッケージ名確定）
PoseFrame pose
sensor_msgs/PointCloud2 points
```

- **生RGB画像を含めない**。ジャーナルから継承する生点群の可変点数も維持する。
- `pose.header.stamp`と`points.header.stamp`の両方をそのまま内包する。**別の合成stampを作らない**。
- **最終メッセージに`SyncPairInfo`は含めないと確定**。含まれる2つの元stampで後から同期時差を確認できる。
- **最上位の追加`Header`や`pair_id`は含めないと確定**。将来サーバ側要件が変わった場合は設計改訂で再検討する。
- Piとサーバが同じメッセージ定義パッケージを参照できることが必要。ROS 2のカスタムメッセージ内には別メッセージ型をフィールドとして配置できる。

### 10.8 集約ノードが保証すべき最小の動作

**正常系**：3トピックが任意の順で到着しても、`SyncPairInfo(rgb_stamp, lidar_stamp)`と完全一致する結果が双方存在した場合に**そのペアを1回だけ**Publishする。別のRGB・LiDARの近傍探索をしない。完了した結果は集約状態から削除する。

**正常な空結果**：`persons=[]`のPoseFrame、およびROI後点数0の`PointCloud2`は、いずれも**正常に届いた処理結果**として扱う。PairInfoと両結果が揃えば空結果を含む`SynchronizedFrame`をPublishする。人物0人／ROI 0点を、推論・点群前処理の失敗や通信欠落と混同しない。

**異常系**：片側の欠落、PairInfo欠落、同じ結果の重複、元stamp不正、起動・再起動後の古いデータを識別・診断する。ただし**欠落・再起動対策自体は集約方式A固有の欠点ではなく、全方式共通の運用要件**。A固有のコストは「別PairInfo経路と3入力管理」。

**採用済みのバッファ破棄**：完成したペアは即Publishして待機データを削除する。未完成のまま待機期限を超えたデータは破棄する。容量上限を超えるときは、最も古い未完成データから1件ずつ押し出し、収まるまで繰り返す。`PairInfo`到着前の姿勢・点群の先着データも保持数／期限の対象に含める。破棄したものを別ペアの値で補完しない。

**暫定初期値（採用済み）**：各入力（`SyncPairInfo`・`PoseFrame`・`PointCloud2`）の待機保持数上限10件、未完成データのタイムアウト1秒。ROS 2パラメータで調整可能にする。**未決定／要検証**：採用済みQoS初期設定の新規経路での実測適合、空点群のメッセージ形式が実機で正しく送受信できること、stamp重複が実際に観測された場合の対処、通常運用のコンソール表示の頻度・書式、初期値の実機適合。**完成順Publishと簡素なコンソール表示は採用済み**で、サーバ側の時系列復元方式は別途決める。

### 10.9 見送った型表現と理由（暫定評価）

| 候補 | 状態 | 理由／再検討条件 |
|---|---|---|
| COCO17を`vision_msgs/Detection2D`だけで表現 | **暫定不採用** | BBox・検出を主とする型であり17関節のXY・score欠損契約をそのまま表すフィールドがない。既存のより適切な共通型があれば再検討 |
| `Keypoint2D.msg`＋`Keypoint2D[17] joints` | **不採用（現段階）** | 関節ごとのX/Y/scoreを束ねて可読性を高められるが、`Keypoint2D.msg`は標準型ではなく追加の独自型。今回のCOCO17固定条件とジャーナルとの対応を優先し、3本の固定長配列を採用。拡張時に再検討可能 |
| `float32[51] keypoints_xyzscore`相当のフラット配列 | **暫定不採用** | 転送量は大差なく、値の順序を取り違えるリスクがある。x/y/scoreの区別が読みやすい方を優先 |
| PoseFrameに`pair_id`追加 | **現段階で不採用** | 集約方式Aの採用理由（前処理ノードへ同期概念を持ち込まない）に反する |
| `SynchronizedFrame`に元RGB Imageを含める | **不採用** | サーバへ画像を送信しないという確定要件に反する |
| 一律`N=256`にしてから送信 | **不採用** | N=256は後段モデル入力の暫定条件であり、ROI後の可変点数保持に反する |
| 毎フレームにモデル名・設定全文を埋める | **現段階で不採用** | 中間メッセージの責務外。設定・再現性ログは別管理する方が簡潔 |

### 10.10 次のレビュー項目

1. **`PersonPose`の実機適合性確認**：COCO17の固定長3配列、BBox・検出スコア、明示的欠損時のNaN三値セットは**採用済み**。Hailo出力を元RGB座標へ変換する処理と、欠損値のデコード仕様は実機で確認する。
2. **確定済みのROS 2インターフェースを実装へ反映**：`PoseFrame`・`SyncPairInfo`・`SynchronizedFrame`のフィールドを増やさず、正常未検出は`persons=[]`で扱う。現行EdgeRM用には`SendSynchronizedFrame.srv`（`frame`／`accepted`）を追加する。
3. **`PointCloud2`のtagフィールドと座標系**：Livoxの`xfer_format=0`・10Hz・`livox_frame`初期値、ROI後XYZ＋`tag`のみの出力、**ROI後0点でも空点群を正常Publishする処理**、LiDAR→専用`fall_detection_frame`への静的TF＋前方固定ROIは承認済み。実ドライバでの`tag`有無・型・変換後の維持、取付TF値・**暫定ROI初期値の適合性**・床基準との整合を確認する。初期実装で傾き補正・追加座標補正は行わない。
4. **確定した内部5トピック名と2パッケージ名**を実装設定へ反映する。ドライバの実トピック名・サーバ側受信ノード名は未決定として確認する。
5. その後、**採用済みQoSの新規経路での実測確認**、**暫定初期値（待機各入力10件・1秒）の実測による調整**、サーバ側時系列処理を設計する。通常の状態確認はコンソール表示で足りるため、詳細ログ保存設計は後回しとする。
